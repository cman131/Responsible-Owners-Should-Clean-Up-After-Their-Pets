# Species-Restricted Item Equipping

## State

Complete

## Summary

Some items can only be held by a specific pokemon species (mega stones like Abomasite, species-exclusive orbs like Adamant/Lustrous Orb, etc.). `HeldItem` has no `speciesRestriction` field, the seed script discards the `megaEvolves` data available from `@pkmn/dex`, and `PokemonSlotEditor` does not filter the item dropdown by the currently selected species. Additionally, once non-equippable items are classified (via the equippable-flag plan), items of that type must be completely blocked from pokemon slots. This plan gates the held-item dropdown by both the equippable flag and any per-species restriction. Depends on the item-type-classification-equippable-flag plan.

## Problem Details

**File:** `data/scripts/seed.ts:160-165`

```typescript
const allItems = gen9.items.all().map((i) => ({
  id: i.id,
  name: i.name,
  effectId: i.id,
  isBerry: !!i.isBerry,
  // ← i.megaEvolves is discarded; this is the species the stone is locked to
}));
```

The `@pkmn/dex` `Item` object exposes `megaEvolves?: string` (the PS species name, e.g. `'abomasnow'` for Abomasite). This data is dropped at seed time and is not recoverable without re-seeding.

**File:** `packages/shared/src/types/pokemon.ts:82-87`

```typescript
export interface HeldItem {
  id: string;
  name: string;
  effectId: string;
  isBerry: boolean;
  // ← no speciesRestriction field
}
```

**File:** `packages/server/src/socket/handlers/adminHandlers.ts:101-112`

The `data:query items` handler accepts no `speciesName` parameter, so the server cannot pre-filter items by species restriction before returning results to the client.

**File:** `packages/client/src/admin/ItemSearchDropdown.tsx:20-29`

The query payload sent to `data:query items` carries only an optional text `query`; no species context is sent. All implemented items are presented regardless of the currently selected species in the slot editor.

## Impact

- Admins can equip Abomasite to a Charizard — invalid combination that would have no effect in battle (or cause engine errors if species-restriction is later enforced in the engine).
- Non-equippable items (once classified) could still appear in the slot editor's dropdown if the equippable filter and species filter are not applied together.
- Species-restricted items clutter the item dropdown for pokemon they cannot be assigned to.

## Suggested Fix

1. Add `speciesRestriction?: string` to `HeldItem` in `packages/shared/src/types/pokemon.ts`. Value is a PS species name (e.g. `'abomasnow'`), absent means no restriction.

2. Update `data/scripts/seed.ts` item mapping to include:
   ```typescript
   ...(i.megaEvolves ? { speciesRestriction: i.megaEvolves.toLowerCase() } : {}),
   ```
   Re-run `pnpm seed` to regenerate `data/items.json`.

3. In `packages/server/src/socket/handlers/adminHandlers.ts`, extend the `data:query items` case to accept an optional `speciesName?: string` param. Filter out items where `item.speciesRestriction` is set and does not match `speciesName`:
   ```typescript
   const { query: itemQuery, equippableOnly, speciesName } = payload.data as { ... };
   const filtered = allImplemented
     .filter((i) => !equippableOnly || i.equippable)
     .filter((i) => !i.speciesRestriction || i.speciesRestriction === speciesName);
   ```

4. In `packages/client/src/admin/PokemonSlotEditor.tsx`, pass the current `value.speciesId` (resolved to a species name) as a `speciesName` prop to `ItemSearchDropdown`, which forwards it in the `data:query` payload.

5. Add a secondary local filter in `ItemSearchDropdown` as a safety net: after receiving results, filter out any item where `item.speciesRestriction` is defined and does not match the prop, to guard against stale results.

6. Non-equippable items (those with `equippable: false` from the equippable-flag plan) must never appear in `PokemonSlotEditor`'s item picker. The `equippableOnly: true` flag from that plan handles this; confirm the two filters compose correctly in the server handler.
